3. COST DECOMPOSITION  (64B, N messages fully handled)
------------------------------------------------------------------------------

The same workload against progressively more expensive paths. Every
row except the first is acknowledged, so these are true 'processed N
messages' rates.

mode                   msgs     sec       msg/s    MB/s  vs floor   stdout B
ps-ingest           300,000   2.601     115,344     7.0      100%          0
ps-nim-echo          30,000   0.661      45,389     2.8       39%          0
ps-hook-noop         30,000   0.457      65,605     4.0       57%          0
ps-hook-echo         30,000   0.731      41,025     2.5       36%          0

HOW TO READ THIS
  ps-ingest and ps-hook-noop are ONE-WAY: inbound only, one thread
  handoff per message (io thread -> worker).
  ps-nim-echo and ps-hook-echo are ROUND TRIP: they add the outbound
  path, which is a second handoff back to the io thread.

  If ps-nim-echo and ps-hook-echo land close together, the Python
  bridge is NOT the limiting factor -- mummy's per-message thread
  handoff is. Optimising the GIL bridge further would then be wasted
  effort for this workload.

NOTES
==============================================================================
* Latency includes the whole client->kernel->server->kernel->client
  loop on loopback. Subtract roughly 20-40us to approximate the
  server-only cost.
* Every Python callback serialises on the GIL. That is inherent to
  CPython, not to pocketsocket's bridge. The ps-nim-* rows show the
  ceiling available when python is not in the message path.

ADDENDUM: RELEASE vs DEBUG BUILD
==============================================================================

`nimble build` injects -d:release automatically. A custom nimble `task` does
NOT, so buildPyd was silently producing an unoptimised extension module
(Hint: "opt: none (DEBUG BUILD)"). Fixed by adding switch("define","release").

Same host, same source, 16 vCPU:

                            debug      release    change
  ps-nim-echo   64B        24,527      45,501     +86%
  ps-nim-echo   1KB        18,014      34,184     +90%
  ps-nim-echo  16KB         4,803      16,904    +252%
  ps-nim-echo  64KB         1,456       6,438    +342%
  ps-hook-echo  64B        23,584      40,989     +74%
  ps-nim-echo   p50        109.1 us     84.1 us    -23%
  conn/s                    3,291       4,885     +48%
  .so size                899,072 B   451,736 B    -50%

Anyone who ran `nimble buildPyd` or `pip install -e .` before this fix was
running a debug build. All earlier result files in this directory are
therefore understated for the python module (the CLI was always -d:release).

==============================================================================
ADDENDUM: THE CEILING IS MUMMY'S SINGLE IO THREAD
==============================================================================

Concurrency scaling, release build:

  ps-nim-echo    1 client   37,246 msg/s
  ps-nim-echo    2 clients  38,902
  ps-nim-echo    8 clients  36,713
  ps-nim-echo   32 clients  34,457

One connection already saturates the server. Adding connections does not
increase aggregate throughput at all -- it very slightly decreases it.

The reason is architectural, and it is not the worker pool. mummy has exactly
ONE io thread: a single Selector (mummy.nim:97) driven by a single
selectInto loop (mummy.nim:1164). Worker threads only execute handlers; every
byte read from and written to every socket passes through that one thread.

  workerThreads  -> parallel handler execution   (scales)
  io thread      -> all socket read/write        (does NOT scale, count = 1)

For an echo workload the handler is trivial, so the worker pool has nothing to
parallelise and the io thread is 100% of the cost. That is why:

  * worker_threads is flat from 1 to 160
  * 8x the cores changes nothing
  * 32 concurrent clients are no faster than 1

IMPLICATION FOR A REPLACEMENT TRANSPORT
---------------------------------------
Any rewrite must have multiple io threads to beat this, e.g. SO_REUSEPORT with
one epoll loop per core and connections sharded across them. Simply removing
the worker-thread handoff (the "direct write from the worker" idea) would help
latency but would NOT lift this ceiling, because the read side is still
single-threaded.

Rough target: the single io thread does ~38k round-trips/sec here. N independent
io threads should approach N x that, until the NIC or the client becomes the
limit. The client ceiling for this harness is ~480k msg/s (section 0), so there
is roughly 12x of headroom to measure into before the benchmark itself needs
reworking.
