3. COST DECOMPOSITION  (64B, N messages fully handled)
------------------------------------------------------------------------------

The same workload against progressively more expensive paths. Every
row except the first is acknowledged, so these are true 'processed N
messages' rates.

mode                   msgs     sec       msg/s    MB/s  vs floor   stdout B
ps-ingest           300,000   2.692     111,423     6.8      100%          0
ps-nim-echo          30,000   1.257      23,862     1.5       21%          0
ps-hook-noop         30,000   0.623      48,154     2.9       43%          0
ps-hook-echo         30,000   1.271      23,604     1.4       21%          0

HOW TO READ THIS
  ps-ingest and ps-hook-noop are ONE-WAY: inbound only, one thread
  handoff per message (io thread -> worker).
  ps-nim-echo and ps-hook-echo are ROUND TRIP: they add the outbound
  path, which is a second handoff back to the io thread.

  If ps-nim-echo and ps-hook-echo land close together, the Python
  bridge is NOT the limiting factor -- mummy's per-message thread
  handoff is. Optimising the GIL bridge further would then be wasted
  effort for this workload.

==============================================================================
ADDENDUM: WHERE THE ~25k msg/s CEILING LIVES
==============================================================================

Per-message cost derived from the section 3 rates:

  ps-hook-noop  48,154 msg/s = 20.8 us/msg   inbound + hook
  ps-nim-echo   23,862 msg/s = 41.9 us/msg   inbound + outbound

  hook invocation (measured separately)  ~5 us
  => inbound path                        ~16 us/msg
  => outbound path                       ~26 us/msg

The outbound path is the dominant cost, and it is mummy internals, not
pocketsocket. mummy's WebSocket.send() encodes the frame, appends it to a
server-wide sendQueue under a lock, then fires a SelectEvent to wake the io
thread (mummy.nim:286-291). In a request/response pattern the send queue is
empty every time, so the wakeup fires on every single message: an eventfd
write plus an epoll wakeup plus a thread context switch, per message.

That is why more cores, more clients and more worker threads all fail to move
the number: the work is serialised through one io thread and paced by a
syscall round trip, not by CPU.

COMPARISON WITH THE 2 vCPU RUN
------------------------------
                        2 vCPU        16 vCPU      change
  ps-nim-echo 1 conn    20,194        22,110       +9%
  ps-nim-echo peak      25,828 (4c)   28,159 (4c)  +9%
  ps-hook-echo peak     19,296 (1c)   29,129 (16c) +51%
  ps-nim-echo p50       86.2 us       109.1 us     worse

8x the cores bought roughly 10-35% throughput and slightly worse latency.
The earlier hypothesis -- that mummy's per-message thread handoff is a cost
that buys cross-core headroom -- is NOT supported by this data.
